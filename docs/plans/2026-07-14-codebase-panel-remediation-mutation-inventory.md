## Latent boundary defects recorded for remediation

- `loans.created_at` is referenced by centralized queries but absent from the current table; this must be resolved before centralization is relied upon.
- `getActiveLoanForItem` currently considers only `approved` and `active`; the reservation contract requires `requested`, `approved`, and `active` to block duplicate requests.
- Existing `staff_actor_id` columns are present on items, loans, posts, memberships, and neighborhoods but are absent from the shared `Loan` type and not consistently selected or written.
- `getAuthContext()` uses an admin client for all staff requests, not only impersonation. Admin-client reads therefore require explicit soft-delete and tenant predicates; RLS cannot be assumed.
- PostgreSQL permissive policies combine. Any replacement must explicitly remove the broad old policy and inspect `pg_policies`.
- The initial `loans.item_id` foreign key is `ON DELETE CASCADE`; the ordinary deletion contract must become non-destructive, while the physical neighborhood teardown remains the only documented exception.

## Inventory completion rule

A mutation is not considered remediated until its caller identity, target identity, tenant scope, database boundary, affected-row behavior, side effects, and named regression test are all explicit. The static inventory script added in Phase 6 will enforce the approved direct-write boundary and the physical-teardown exception.
